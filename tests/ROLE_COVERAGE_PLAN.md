# خطة تغطية اختبارات الصلاحيات حسب الدور

تاريخ الإعداد: 2026-11-20

## 1. الوضع الحالي

ملف الاختبار الحالي `tests/cloud-smoke.spec.cjs` يستخدم بيانات دخول واحدة فقط:

- `TEST_USERNAME`
- `TEST_PASSWORD`

بعد تسجيل الدخول، يجمع الاختبار الأقسام الظاهرة للحساب ويزور كل قسم متاح. كما يفحص بعض عناصر الواجهة والصلاحيات الظاهرة، ثم يسجل الخروج.

هذا يختبر جلسة حساب واحد، ولا يمثل اختبارًا مستقلًا للأدوار السبعة. كما أن إخفاء قائمة أو زر لا يثبت وحده حماية قاعدة البيانات.

الاختبار الحالي للقراءة فقط ولا ينشئ مستندات مالية أو حركات مخزون.

## 2. الأدوار التي يجب اختبارها

يجب تخصيص حساب اختبار مستقل لكل دور:

| الدور | حالة التغطية المستقلة |
|---|---|
| SYSTEM_ADMIN | غير مكتملة |
| SALES_MANAGER | غير مكتملة |
| SALES_REP | غير مكتملة |
| WAREHOUSE_KEEPER | غير مكتملة |
| PRODUCTION_MANAGER | غير مكتملة |
| ACCOUNTANT | غير مكتملة |
| GENERAL_MANAGER | غير مكتملة |

لا تعتبر نتائج حساب الاختبار الحالي دليلًا على اجتياز الأدوار الأخرى، حتى لو كان الحساب الحالي يملك صلاحيات واسعة.

## 3. الاختبارات المطلوبة لكل دور

1. تسجيل الدخول والخروج واستعادة الجلسة.
2. قراءة الدور الفعلي للحساب من بيانات الجلسة أو ملف المستخدم.
3. مقارنة القوائم والأقسام الظاهرة بمصفوفة الصلاحيات المعتمدة في التطبيق وقاعدة البيانات.
4. التأكد من إخفاء الأزرار والإجراءات غير المسموحة.
5. التأكد من أن محاولة فتح قسم غير مسموح به مباشرة لا تعرض بياناته.
6. فحص الوصول للقراءة إلى البيانات التي يسمح بها الدور، ورفض القراءة التي تمنعها سياسات RLS.
7. فتح الشاشات المسموح بها والتأكد من اكتمال تحميل البيانات وعدم ظهور أخطاء JavaScript أو الشبكة.
8. تسجيل نتيجة كل دور منفصلة مع الأقسام المسموحة والمخفية والأخطاء.

## 4. اختبارات إضافية حساسة

تحتاج هذه الحالات إلى مراجعة صريحة لمصفوفة الصلاحيات قبل تشغيلها:

- اعتماد طلب تحميل السيارة، ويجب ألا يختلط مع تأكيد أمين المخزن للصرف الفعلي.
- فحص مرتجع المبيعات، مع فصل اعتماد أمين المخزن عن اعتماد مدير الإنتاج.
- إدارة قوائم الأسعار وحدود خصم المندوب.
- إدارة الخزائن والتحصيلات والتسويات.
- القيود والتقارير المحاسبية.
- إدارة الشركاء وحركات رأس المال.
- إرسال الإشعارات العامة وإشعارات المهام، وهي لمدير النظام فقط.

في مرحلة التغطية الأولى، نتحقق من ظهور عناصر الواجهة والقراءة فقط. لا ننفذ اعتمادًا أو إلغاءً أو صرفًا أو تحصيلًا أو أي RPC يغيّر البيانات.

## 5. متطلبات بيئة الاختبار

سياسة المشروع هي عدم إضافة أي تكلفة تشغيلية جديدة. لذلك لا تنشئ فرع Supabase مدفوعًا، ولا تطلب ترقية الخطة أو تفعيل خدمة مدفوعة.

تُستخدم فروع GitHub المجانية لمراجعة ملفات الاختبار فقط. فرع GitHub لا يعزل قاعدة البيانات، ولذلك لا يُعد بديلًا عن بيئة Supabase منفصلة.

لا تشغّل اختبارات العمليات التي تنشئ أو تعدّل بيانات على قاعدة التشغيل. تقتصر الاختبارات السحابية الحالية على تسجيل الدخول والقراءة والتنقل وفحص الواجهة، مع تجنب أي إجراء يغيّر البيانات.

تُستخدم حسابات الأدوار الموجودة بالفعل فقط، إذا توفرت. لا تنشئ حسابات أو تغيّر أدوارًا أو صلاحيات في قاعدة التشغيل ضمن هذه المرحلة. إذا لم يتوفر حساب لدور معين، تسجل تغطيته على أنها غير منفذة بدلًا من استخدام حساب بديل.

لا تُختبر إجراءات الكتابة أو الاعتماد أو الإلغاء أو الصرف أو التحصيل حتى تتوفر بيئة اختبار معزولة دون تكلفة إضافية أو يوافق المستخدم صراحة على بديل آمن.

يمكن إضافة أسرار GitHub Actions منفصلة لكل دور، أو سر واحد منظم يحتوي بيانات الحسابات السبعة. لا تُحفظ كلمات المرور داخل المستودع أو ملفات الاختبار.

## 6. تعديل GitHub Actions المطلوب لاحقًا

الـworkflow الحالي يمرر حسابًا واحدًا عبر `TEST_USERNAME` و`TEST_PASSWORD`.

بعد التأكد من وجود حسابات اختبار مستقلة بالفعل، يمكن إضافة أسرار GitHub منفصلة لكل دور وتشغيل اختبار قراءة فقط لكل حساب. لا تُضف أسرارًا وهمية ولا تجعل غياب حساب دور يؤدي إلى استخدام حساب دور آخر.

يجب أن ينتج تقرير مستقل لكل دور يوضح:

- الدور والحساب الاختباري دون إظهار كلمة المرور.
- الأقسام التي ظهرت.
- الأقسام التي حُجبت.
- نتائج فحص القراءة وRLS.
- أخطاء الصفحة والشبكة.
- الاختبارات التي تم تخطيها بسبب غياب بيانات اختبار.

لا يبدأ هذا التعديل قبل تجهيز الحسابات السبعة وتحديد مصفوفة الصلاحيات المعتمدة من التطبيق وقاعدة البيانات.

## 7. معيار الإغلاق

لا تعتبر تغطية الأدوار مكتملة إلا بعد اجتياز الأدوار السبعة كلٌّ بحسابه، وتوثيق السماح والمنع لكل مجموعة صلاحيات، ثم تشغيل اختبارات الإجراءات التي تغيّر البيانات على بيئة منفصلة.

## 8. سياسة التنفيذ المجاني

1. كل مراجعة أو تعديل يبدأ على فرع GitHub منفصل.
2. لا يُنشأ فرع Supabase مدفوع ولا تُفعّل أي خدمة مدفوعة.
3. لا تُنفذ تغييرات على قاعدة التشغيل أو بياناتها أو صلاحياتها دون موافقة صريحة.
4. لا تُنفذ اختبارات كتابة على قاعدة التشغيل.
5. يُسمح باختبارات قراءة فقط باستخدام الحسابات الموجودة بالفعل، مع توثيق الحساب والدور اللذين اختُبرا.
6. لا يُدمج أي تعديل في `main` قبل مراجعة نتيجته.

## 9. ما تم وما لم يتم

- تم تحليل ملف الاختبار الحالي وتحديد أنه يعتمد على حساب واحد.
- تم توثيق خطة التغطية المطلوبة للأدوار السبعة.
- تم إنشاء فرع GitHub مجاني للمراجعة باسم `qa/zero-cost-role-coverage-2026-11-20`.
- لم يُنشأ أي فرع Supabase ولم تُطلب أي ترقية أو خدمة مدفوعة.
- لم تتغير قاعدة البيانات.
- لم تتغير واجهة التطبيق أو ملف الخدمة.
- لم تُنشأ حسابات أو معاملات اختبار.
- لم تُشغّل اختبارات جديدة على قاعدة التشغيل.

يتحقق الاختبار من أن الدور الفعلي داخل جلسة التطبيق يطابق الدور المطلوب، ثم يسجل القوائم الظاهرة والمخفية وأخطاء الصفحة في تقرير مستقل. إذا غابت بيانات أي دور، يتخطى الاختبار ولا يستخدم حسابًا بديلًا.

هذا الاختبار لا يثبت وحده صحة مصفوفة الصلاحيات أو سياسات RLS. يحتاج ذلك إلى مصفوفة معتمدة وحسابات مناسبة وبيئة آمنة. تسجيل الدخول الحالي في التطبيق يحدث بيانات آخر دخول وسجل النشاط، لذلك لا يُشغّل هذا الاختبار على قاعدة التشغيل قبل موافقة صريحة على أثر تسجيل الدخول أو توفير بيئة اختبار معزولة.
